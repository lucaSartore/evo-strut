\chapter{Support Optimization Algorithm}
\label{cha:support_opt_alg}


\section{Pipeline Overview}
\label{sec:pipeline_overview}

The support structure optimization algorithm we are proposing is organized ino a pipeline
composed of 8 steps, of those the first and last are simple I/O steps (namely Importing and Exporting).
Then the steps two to four (Criticality Detection, Floating Regions Detection and Criticality Grouping)
are simple pre-processing steps that perform some operations in order to prepare data for the following
steps.
Finally steps five to seven (Contact Points Optimization, Contact Points Grouping and Support
Structure Optimization) are the real ``Optimization'' steps, that perform the optimization
of the actual support. This operation is performed in three stages, rather than a single optimization 
process for a more efficient computation, infact we can assume that the decision about where to place
contact points in the areas to support is (roughly) independent from the decision on how to build a
structure that reach those points, this allow to take the decision separately, and have two simpler
problems instead of one complex one. This approach is quite common in literature, infact it has
been used by Zhang et. al. \cite{ZHANG2020117} (the second paper we cited in the previous literature chapter).
The following lists show the steps of the pipeline in order, with a small description of what they do:

\begin{itemize}
    \item \textbf{Importing:} This step load the model and perform some simple re-meshing operations in order
    to reduce the amount of triangles in the mesh in order to obtain better performances.
    \item \textbf{Criticality Detection:} This step detect the critical regions (the points where the
    surface is too steep, and a support is required)
    \item \textbf{Floating Regions Detection:} This step detect the ``Floating regions'' (areas
    of the model that, while being printed are completely detached from the plate for a period of time,
    as the connection is provided by layers above)
    \item \textbf{Criticality Grouping:} This step groups the critical areas detected in the step 2 into
    some areas that can be optimized separately (for more efficient computation)
    \item \textbf{Contact Points Optimization:} This step identify an optimal set of points where
    supports will be placed using a genetic algorithm and a cost function.
    \item \textbf{Contact Points Grouping:} This step group the contact points into areas based on proximity,
    this step is once again performed in order to optimize the different areas separately.
    The optimization is done using a Compositional Pattern Producing Network Based Genetic Algorithm.
    \item \textbf{Support Structure Optimization:} This step optimize the support structure using a genetic
    algorithm, this step is where the stiffness evaluation algorithm we developed previously is used.
    \item \textbf{Exporting:} In the final step we generate a support structure in a mesh based 
    on the optimized parameters, the structure is then exported in STL format.
\end{itemize}


\section{Importing}
\label{sec:importing}

The importing stage is conceptually very simple, A mesh of the object we want to generate support for
is loaded, and then re-meshed.
Re-meshing is a simple procedure that involve starting from a mesh that represent 
a specific object, and then apply a transformation with the aim of obtaining a different
mesh, that represent the same object, using a different set of triangles that satisfy 
some specific properties.
figure \ref{fig:remeshing} show three different meshes that represent the same object,
the first one is minimizing the number of triangles necessary to describe the object,
but is resulting in a set of triangles that is very irregular. The second image show
a re-meshing of the first one, where triangles are divided into smaller and smaller pieces
in order to obtain more regular triangles. The third one is also a re-meshing, but 
it is a more aggressive one, and results in smaller triangles.
For this project we have used an incremental remaster (an algorithm that perform 
recessing by means of progressively splitting and merging triangles in order to obtain
some desired properties). The specific implementation was taken from the popular
rust library ``baby-shark'' \cite{babyshark}.

\begin{figure}[h]
    \centering
    \includegraphics[width=0.5\textwidth]{images/remeshing.png}
    \caption{Example of a re-meshing operation (source: \cite{remeshing})}
    \label{fig:remeshing}
\end{figure}

There are two reasons why re-meshing is applied as part of the loading stage.
The first one is purely a performance reason, infact in order to generate support structure
we don't need an high definition mesh, instead a good approximation is enough. For this reason
the re-meshing process target an edge length in the range of 0.3 - 1.0 mm. this provide a sufficient
level of accuracy while also resulting in a manageable number of triangles, even for large meshes,
which helps the algorithm's performance.
The second reason why re-meshing is important has to do with the representation of the mesh
in the algorithm, infact the last step of the loading procedure is converting 
the mesh into a set graph, where every triangle is a node, and each node is connected
to three other neighbors (one for each side of the triangle.)
Generally speaking we would want all triangle to be as close to an equilateral as possible,
in such a way every connection inside the graph would have ruffly the same length; This
fact is a precondition necessary for the correct functioning of the next stages in the pipeline.
The re-meshing algorithm is therefore also used to ensure triangles have ruffly the same size,
and are ruffly equilateral.

\section{Criticality Detection}
\label{sec:crit_detection}

The first step in the generation of automatic support is of course knowing what zones must be supported.
Generally speaking the presence of a support or not is usually achieved with a simple check of the 
overhanging angle (as we already in the introduction \ref{sec:role_of_sup}).
One of the most basic technique for criticality detection is to simply take angle formed by the 
surface normal of a triangle, and a vector facing downward, and compare that to the threshold of what
is consider acceptable, in order to detect the critical areas.
Most 3D printing software use methods derived the one we just described with a few refinement
key refinements such as for example bridge detection, detection of areas that are ``floating''
etcetera. Our method also inspired by that basic idea, but is slightly different from the 
methods currently used in most commercial 3D printing software, as it's built with a different 
paradigm. Instead of simply detecting a simple boolean value that tell if a surface is critical
or not, our method aim to provide a cost function that, if minimized, reduces the amount of critical
areas there are in a specific model. The reason why this approach was chosen is straightforward, as 
is a simple consequence of the fact that we will need a cost function in order to apply a genetic-algorithms
based optimizer in the following steps.

Now that we explained the reasoning behind the creation of a custom solution for criticality detection
we can begin explaining our implementation. Algorithm \cref{alg:crit_det} show the pseudo-code of 
our implementation of a criticality detection procedure.
The key idea behind our solution is to assign to every node in the mesh graph a ``criticality''.
then the critical node are the one that have a criticality different than zero. This model has the benefit
that it can be easily transformed into a cost function by summing all the criticality score and 
weighting them by the area of the triangle they are associated to.
The second key idea that our solution brings to the table is the concept of ``criticality propagation''
This concept represent the fact that criticality is not an arbitrary value assigned to every single
triangle, regardless of the neighbors, instead the criticality is ``propagated'' from the bottom to the
top. This means that criticality increases every time the object have an overhanging angle that is too hig,
and decreases every time the criticality angle is too low. This is important because otherwise, a single
triangle inside the mesh with a sufficiently low overhanging angle would make an entire zone
less critical, or in the same way a single support could singlehandedly make a large critical area
no longer critical. Figure \ref{fig:critical_detect} show a mesh of a dragon, with the green areas
being the meshes with a criticality score of zero, while the red areas are the critical one.
In here we can see the effect that criticality propagation has on the structures.
in the bottom part of the dragon's wing we can see that the critical area is quite large,
even tho, the overhanging angle is quite small. We can get a sense on why propagation is important
by looking at figure \ref{fig:critical_detect_no_prop} and \ref{fig:critical_detect}.
In the former we see what are the critical regions if no propagation is applied, mean while in the second one
we see the same output, but propagation are applied. Te most notable difference is in the bottom part
of the dragon's wing, as we can see, in the version with no propagation there is a tiny critical area
in the tip of the wing, but as soon as the overhanging angle is small enough, the critical are disappear.
In contrast in the version that has propagation the criticality start at an high value in the top bottom
part of the wing, and require a bit of time for the score to reach zero, resulting in a much larger critical
region. This behavior is desirable, as is unreasonable to think that a single support in the tip of the wing
is enough to support the entire area, meaning that criticality propagation play a key role in detecting
more realistic critical regions when some part of the model are ``floating''.

\begin{algorithm}[H]
\caption{Criticality Detection}
\begin{algorithmic}[1]
    \Require $G$ Graph that represent the mesh
    \Ensure $C$ Dictionary that associate a cost for every node in the graph

    \Procedure{LayerOf}{$n$} \Comment{Calculate the layer of node $n$}
        \State \Return $\left\lfloor{\frac{\Call{Height}{n}}{L_{height}}}\right\rfloor$
    \EndProcedure

    \Statex

    \Procedure{PropagationCost}{$G, f, t$} \Comment{Calculate propacation factor of the link $f$(rom) $t$(o)}
        \State $\varphi \gets \Call{AngleBetween}{f, t}$ \Comment{We start from the angle between the two nodes}
        \State $\varphi' \gets \varphi - \varPhi_t$ \Comment{We compared to the threshold, as small gradients are OK}
        \State $\varphi'' \gets \Call{Clamp}{\varphi', \varPhi_{lb}, \varPhi_{ub}}$ \Comment{We clamp it, to avoid too high propagation factor}
        \State $d \gets \Call{Distance}{f, t}$ \Comment{Distance factor (long distance are more critical than short one)}
        \State \Return $K_{prop} \cdot d \cdot \varphi''$
    \EndProcedure

    \Statex

    \Procedure{CriticalityOf}{$G, n, \mathcal{M}$}
        \If {$\Call{Height}{n} = 0$} \Comment{Nodes to the ground are never critical}
            \State \Return 0
        \EndIf
        \State $c \gets $ CRITICALITY\_MAX \Comment{Initialize criticality at max value}
        \For{$a \in \Call{AdjacentNodes}{G, n$}} \Comment{Iterate over adjacent nodes}
            \If {$\Call{LayerOf} {a} <= \Call{LayerOf}{n} \land a \in M$}
                \State $c_a \gets M(a) + \Call{PropagationCost}{a, n}$
                \State $c \gets \Call{Min}{c, c_a}$
            \EndIf
        \EndFor
        \State \Return $\Call{Max}{c, 0}$ \Comment{Criticality is always greater of equal than zero}
    \EndProcedure

    \Statex

    \Procedure{PropagateInLayer}{$G, l, \mathcal{M}$}
        \State $ PriorityQueue \gets \emptyset$
        \For{$n$ in $l$} \Comment{Initialize the priority queue with the cost propageted by the laeyer below}
            \State $c \gets \Call{CriticalityOf}{G, n, \mathcal{M}}$
            \State $\Call{Push}{PriorityQueue, n, c}$
        \EndFor
        \While {$\lnot \Call{Empty}{PriorityQueue}$}
            \State $n, c = \Call{Pop}{PriorityQueue}$ \Comment{Extract node with the lowest criticality}
            \State $\mathcal{M}(n) \gets c$ \Comment{Mark the criticality in the memory}
            \For{$a$ in \Call{Adjacent}{$G, n$}} \Comment{Neighbors might now have lower criticality, update them}
                \State $c \gets \Call{CriticalityOf}{G, a, \mathcal{M}}$
                \State $\Call{TryUpdatePriority}{PriorityQueue, a, c}$
            \EndFor
        \EndWhile
        \State \Return $0$;
    \EndProcedure
    
    \Statex

    \Procedure{CriticalityDetection}{$G$}
        \State $C \gets \emptyset$

        \For{l in \Call{Layers}{$G$}}
            \State \Call{PropagateInLayer}{$G, l, C$} \Comment{Propaget the cost one layer at a time}
        \EndFor

        \State \Return $C$
    \EndProcedure
\label{alg:crit_det}
\end{algorithmic}
\end{algorithm}


\subsection{Algorithm Overview}
To explain \cref{alg:crit_det} we must start from the concept of layer.
Eery node in a graph is assigned to a layer (represented by an integer value),
the ``LayerOf'' function simply associate a node with is layer, and is simply using
the node's height as the discrimination factor;
The reason why layers are important is that the criticality can be propagated only from
elements of the same layer, or layer below, it can't go below a layer.
The function ``PropagationCost'' take as input two nodes, and calculate the cost that 
is propagated from one to the other in a specific direction, this means that if
node $A$ has criticality $c_a$ and the propagation cost from node $A$ to node $B$ is
$c_{ab}$ than the cost at node $B$ will be upper bounded by he value $c_a + c_{ab}$.
This is an upper bound because it can always be lower if node $B$ has another neighbor
from which it can propagate a lower cost.
It should be noted that this function can return a negative value, this is the case when 
the angle between the two nodes is below the threshold of the maximum overhanging angle, 
and therefore the criticality should decrease.
The function ``CriticalityOf'' is used to calculate the criticality of a node, starting
from nodes that are close to it; In the function we can see how if the node is close to the
ground the criticality is zero (this is obvious, as if a node is attached to the plate it does
not need any support), otherwise the criticality is initialized to the maximum possible value,
and then is reduced if a path is found to propagate a lower criticality value from a neighbor.
The neighbor in order to be eligible must be part of a layer that is the same or lower as the node
currently being evaluated.
Now that we have explained the few ``utility'' functions we can tackle the core part of the algorithm,
this is composed of the two functions ``PropagateInLayer'' and ``CriticalityDetection''.
the idea is that the criticality is propagated from bottom to top, then odes in the graph are organized
in layers, and layers are evaluated from the lowest to the hightest.
The process of evaluating a layer is essential a one pass of a Dijkstra algorithm, where nodes
are explored form the one with the lowest criticality value to the one with the highest.
This process ensure low time complexity while ensuring that every node has the correct criticality value.

\section{Floating Regions Detection}
\label{sec:floating_regions_detection}

Another important pre-processing step is the detection of ``Floating Regions''
As we mentioned in the introduction, a floating region is defined a part of the structure that that while being printed,
is not fully connected to the build plate if not for supports. For example
figure \ref{fig:floating_regions} show the floating regions of the mesh ``Dragon''
highlighted in different colors, while the plain mesh white.
In this section we will not explain why detecting floating regions is necessary,
as that topic will be extensively covered in one of the next sections (specifically \ref{sec:sup_struct_opt_cf}).

    \includegraphics[width=0.5\textwidth]{images/floating_regions_detect.png}
    \caption{Detected floating regions for the test-mesh ``Dragon''}
    \label{fig:floating_regions}
\end{figure}

\subsection{Algorithm Overview}

Efficient detection of floating regions can be achieved using algorithm \cref{alg:float_det}
the idea is that the nodes are sorted from the lowest to the highest, then they are sampled one by one,
and, then visiting the all the nodes reachable form the point, where an arch that go from $A$ to $B$ is 
considered valid only if the layer of $B$ is grater or equal to the layer of $A$.
This ensures that we cannot go ``downward'' when exploring the graph, and therefore that
we cannot explore a floating region unless we start from a point inside that floating region.
While the graph is being explored, we mark nodes that have been visited to avoid visiting the same
node twice, and increasing the time complexity. Once an exploration is completed we can decide if
the explored area is a floating region or not. This can be simply done by checking if the height
of the ``source'' node is equal to zero (or at least is below a certain threshold),
if this is the case we can say that the source was attached to the ground, and therefore
the region is not floating. If this is not the case however, the area we have explored must be a 
floating region. We can also be sure that the nodes we have extracted is the lowest point in the region,
thanks to the sorting we did at the beginning. The sorting also ensures that we start exploring from
the nodes that are close to the ground, avoiding a situation where a floating region is expanded
too much and reach zones that are actually not considered ``floating''.

\begin{algorithm}[h]
\caption{Floating Regions Detection}
\begin{algorithmic}[1]
    \Require $G$ Graph that represent the mesh
    \Ensure $\mathcal{F}$ Set of floating regions 

    \Procedure{ExploreUpward}{$G, s, V$} \Comment{Collect the component reachable going up from $s$}
        \State $R \gets \emptyset$
        \State $Q \gets \{s\}$ \Comment{Initialize the queue with the node}
        \While{$\lnot \Call{IsEmpty}{Q}$} \Comment{repeat untill queue is empty}
            \State $n \gets \Call{Pop}{Q}$
            \State $V(n) \gets true$
            \State $R \gets \Call{Append}{R, n}$
            \For{$a \in \Call{Adjacent}{G, n}$ with } \Comment{Explore adjacent neighbors}
                \If{ $\Call{LayerOf}{a} \geq \Call{LayerOf}{n} \land \lnot V(a)$ } \Comment{Filter by non visited, and $\geq$ layer}
                    \State \Call{Push}{Q, a}
                \EndIf
            \EndFor
        \EndWhile
        \State \Return $R$
    \EndProcedure

    \Statex


    \Procedure{FloatingRegionsDetection}{$G$}
        \State $\mathcal{F} \gets \emptyset, \quad V \gets \emptyset$ \Comment{Detected regions and visited nodes}
        \For{$s \in \Call{SortNodesByHeight}{G}$}
            \If{$V(s)$}
                \State \textbf{continue} \Comment{Already part of a component}
            \EndIf
            \State $R \gets \Call{ExploreUpward}{G, s, V}$ \Comment{Exploring grpah, while only moving ``uppward''}
            \If{$\Call{HeightOf}{s} > 0$} \Comment{If the node is detached from the ground}
                \State $\mathcal{F} \gets \Call{AddFloatingRegion}{F, R}$ \Comment{Mark the explored node as a floating region}
            \EndIf
        \EndFor
        \State \Return $\mathcal{F}$
    \EndProcedure
\label{alg:float_det}
\end{algorithmic}
\end{algorithm}



\section{Criticality Grouping}
\label{sec:criticality_grouping}

In this stage in the pipeline we have a set of nodes inside the mesh graph that is deemed
``critical'' however we have no grouping or topology of the critical area themes.
This is not strictly speaking an issue, as we could in theory execute the next stage (contact
points optimization) only once, for the entire set of critical regions, however this would 
be less then ideal from a performance standpoint. Infact, generally speaking in this kind of 
optimization problems is generally more efficient to optimize many small problems rather than
one big one. Furthermore due to the way we are defining our cost function (that we will
explain more in section \ref{sec:contact_points_opt_cf}) the cost of one set
of connected critical nodes is independent from the cost of another set of critical
nodes. With those two facts in mind, it is easy to see why grouping the contact points
based on proximity, and optimize each of them as a separate problem would be convenient
from a performance standpoint, while not impacting the output of the optimizer.
For this reason we made the choice of inserting the ``Criticality Grouping'' stage
in the pipeline, so that we could create a sensible grouping of the critical regions,
with the objective of optimizing them separately.
Algorithm \cref{alg:crit_grouping} show the procedure of how grouping is executed.

\subsection{Algorithm Overview}

\begin{algorithm}[h]
\caption{Criticality Grouping}
\begin{algorithmic}[1]
    \Require $G$ Graph that represent the mesh
    \Require $C$ Set of critical nodes detected
    \Ensure $R$ Grouped set of critical nodes

    \Procedure{Explore}{$G, C, s, V$} \Comment{Collect the critical nodes reashable from $s$}
        \State $R \gets \emptyset$
        \State $Q \gets \{s\}$ \Comment{Initialize the queue with the node}
        \While{$\lnot \Call{IsEmpty}{Q}$} \Comment{repeat untill queue is empty}
            \State $n \gets \Call{Pop}{Q}$
            \State $V(n) \gets true$
            \State $R \gets \Call{Append}{R, n}$
            \For{$a \in \Call{Adjacent}{G, n}$ with } \Comment{Explore adjacent neighbors}
                \If{ $n \in C \land \lnot V(a)$ } \Comment{Filter by non visited, and critical nodes}
                    \State \Call{Push}{Q, a}
                \EndIf
            \EndFor
        \EndWhile
        \State \Return $R$
    \EndProcedure

    \Statex


    \Procedure{CriticalityGrouping}{$G, C$}
        \State ${R} \gets \emptyset, \quad V \gets \emptyset$ \Comment{Grouped regions and visited nodes}
        \State ${N} \gets \Call{Dijkstra}{G, start=C, max\_distance=D_{max}}$
        \State $C \gets C \cup N$ \Comment{Consider critical all nodes that are closer than $D_{max}$ to a critical node}
        \For{$s \in C$}
            \If{$V(s)$}
                \State \textbf{continue} \Comment{Already part of a component}
            \EndIf
            \State $C \gets \Call{Explore}{G, C, s, V}$ \Comment{Exploring grpah, while only moving ``uppward''}
            \State $R \gets \Call{AddGroup}{R, C}$
        \EndFor
        \State \Return $R$
    \EndProcedure
\label{alg:crit_grouping}
\end{algorithmic}
\end{algorithm}

In the algorithm \cref{alg:crit_grouping} we can see that the ``grouping'' operation mainly
involve two steps, the first one is to apply a ``dilation'' to the critical nodes. This dilation
is characterized by a specific parameter ($D_{max}$) that represent the distance of a dilation.
During the dilation operation, every node that have at least one critical node closer than $D_{max}$
is considered as well critical. This dilation is applied in order to ``merge'' critical regions
that are really close together in order to reduce the total number of regions the algorithm 
will produce. The reasoning behind this erosion is that, although it is true that generally speaking
small optimization problem are easier to solve than a single bigger one, this reasoning has a limiting.
and we found that, if a mesh has a large area that is very close to the overhanging angle, the
criticality detection algorithm would generate a very large subset of tiny critical areas.
This was an undesirable behaver, therefore this dilation was added so that by tuning $D_{max}$
we are able to control how ``aggressively'' critical regions are divided into groups.
of $D_{max}$ is set to zero we get the highest number of groups, while if we increase the value
we gradually reduce the amount of groups that are generated.
The second stage in the grouping algorithm is the exploration of the graph itself,
in this stage we start from every critical point, and we explore the graph by navigating
to all the nodes that are marked as ``critical'', in this stage we keep track of then nodes that are 
visited so to avoid visiting the same node twice, and increasing the time complexity;
And finally, once all the nodes that are reachable form a source, we can mark those nodes
as a ``critical group'' (i.e. a set of critical nodes that are all connected to each others).



\section{Contact Points Optimization}
\label{sec:contact_points_opt}

The objective of this stage is to decide the ``contact points'' (i.e. where the supports
will make contact with the printed object in order to provide a support interface).
This step is done independently from the true optimization of the support structure.
Generally speaking it is not true that the two choices are independent from each others, infact
we can easily imagine a scenario where placing a contact point in a specific position
reduces the cost function for the contact points by a bit, but introduces more cost
in the generation of the support structure. However, even tho they are not purely independent
from each others, they are not excessively correlated, meaning that separating the two stages
does not introduces excessive quality loss. For this reason separating the two stages
can be considered a good idea, infact other related works such as Zhang et. al. 2020 \cite{ZHANG2020117}
have done exactly the same. Our method is not drastically different from theirs,
it of course have slightly different cost function and optimization process, but 
realistically speaking, in terms of novelty our approach for contact points optimization
does not have to offer much (the same cannot be sed for the next two optimization stage).
The optimization of contact point is achieved with a genetic algorithm, therefore
the explanation of inner working of the algorithm is explained in separate sections,
once for every component of the genetic algorithm (cost function, gene, mutation crossover
and optimization process).
Figure \ref{fig:contact_points_opt} show the result of the optimization process, where the contact
points are represented with a small purple dot on top of the critical area (the radius however is
not visualized). We can see how the result is not particularly interesting, as it basically looks
a sample of equally spaced points inside the critical area. This makes sense as generally speaking
a good support structure satisfy exactly that condition, however this shows us how complex
genetic-algorithm optimization is not always necessary for every task. Infact this optimization
stage is probability the less useful of the three, and could easily be replaced by a simpler and faster
``greedy'' algorithm that would perform very similarly.

\subsection{Gene Structure}
\label{sec:contact_points_opt_gs}

The genetic representation of a contact points choice is incredibly straightforward,
is essentially a set of the nodes in the graph that we decided to place a support on,
with every node having a ``radius'' associated with it (allowing the algorithm
a bit of flexibility, in deciding whether it is more advantageous to use one large
support or many smaller supports)
From this gene it is possible to derive the set of supported nodes,
this is done by drawing a circle around the node, and selecting the support
that are in the perimeter (the use of the perimeter rather than all the circle's area
is due to the way supports are generated. Since they are ``empty'' cones, they
do not provide any support in the center of cone's base, but only on the perimeter,
nevertheless this part will be explained more thoroughly in the exporting section \ref{sec:exporting})

\subsection{Cost Function}
\label{sec:contact_points_opt_cf}

The cost function is derived from the criticality detection algorithm \cref{alg:crit_det}.
As we explained in section \ref{sec:crit_detection} the output of the algorithm is
a dictionary that map every node in the surface graph to it's criticality vale. and
starting from this dictionary is possible to find the total cost by summing
all the individual costs and weighting them by the node's area.
Nonetheless we are still required to make a few changes to the algorithm
in order to use it as the cost function.
The necessary changes can be seen in algorithm \ref{alg:contact_points_opt_cf},
the first one (at line 2) is straightforward, as it is simply 
introduce in the evaluation procedure the effect of supports. Infact the previous version
of the algorithm did not consider supports at all, now however
we must keep track of where the supports are, and in that case that node $n$
is one of the nodes supported we automatically assign it's criticality to zero.
The second change to the algorithm is a bit less trivial to explain.
We can see that at line 6 we added to the final cost a portion of the ``base cost''.
The base cost of $n$ is defined as the cost that node $n$ would have, if no supports were applied.
$\alpha$ is a small scalar (in our final tests we used 0.03) that represent how much of the
base cost is ``passed'' back when evaluating the structure with supports enabled.
The reason of this modeling choice, has to do with floating regions.
As we can remember form section \ref{sec:crit_detection} the propagation factor
was added to avoid detecting only a tiny critical region in some particular
scenarios such as for example the wing of the dragon 
(see figure \ref{fig:critical_detect} and \ref{fig:critical_detect_no_prop}).
Without this cost term, a single well-placed support in the ``tip'' of the dragon's wing
would singlehandedly remove the entire critical region, however in real life such a
support would create many problems, both because of the z-wobble effect (\ref{sec:wobble-test})
and because when printing the connection between supports and the model is constructed
to be fragile on purpose, in order to simplify the removal process, making it extremely
likely that the wing would detach from the support before it manage to connect to the body
of the dragon.
The addition of the base cost make it so that, when propagating,
the criticality value has a tendency to drift towards th value it would have
had in the case where no supports where added. This is a simple trick that allow
floating regions to be handled correctly and avoid the issues we desired.


\begin{algorithm}[h]
\caption{Updates to criticality }
\begin{algorithmic}[1]
    \Procedure{CriticalityOf}{$G, n, \mathcal{M}$}
        \If {$\Call{Height}{n} = 0 \lor \textcolor{red}{\Call{IsSupported}{n}}$}
            \State \Return 0
        \EndIf
        \State ...
        \State \Return $\Call{Max}{c, 0} + \textcolor{red}{\alpha \cdot \Call{BaseCost}{n}}$
    \EndProcedure
\end{algorithmic}
\label{alg:contact_points_opt_cf}
\end{algorithm}

The cost associated with the criticality is only half of the equation of course,
Infact if that was the only cost we applied to the optimizer the optimal solution
would be as simple as placing a support on every critical node in the graph.
This is of course ideal from a quality of support standpoint, but is less than ideal
if we consider the cost of the material used for the supports.
For this reason the second part of the cost is a simply derived from a unit cost
for every support placed, plus a linear cost proportional to the area of the support
circle.

\subsection{Mutations}
\label{sec:contact_points_opt_mut}

Since the gene we used to represent the contact points is quite simple, the
genes mutations applied can also be simple. We have designed four fundamental
mutations, so that every time a gene need to be mutated we can simply
select one or more fundamental mutations, and apply them sequentially to the gene.
The four fundamental mutations are:
\begin{itemize}
    \item \textbf{Add Support:} This mutation picks a random node from the list of critical
    one and place a new support with a randomly generated radius on it.
    \item \textbf{Remove Support:} This mutation picks a random support from the gene
    and removes it
    \item \textbf{Move Support:} This mutation pks a random support, and move it to a different
    node, when selecting the new node only nodes that are within a certain radius of the original
    one are considered eligible.
    \item \textbf{Change Support Radius:} This mutation increases or decreases the radius
    of the support by some random value, while ensuring the radius stays within some
    predetermined margins.
\end{itemize}

\subsection{Crossover}
\label{sec:contact_points_opt_cross}

The crossover strategy is simple to explain, given two genes, a random plane is generated
in 3D space, then we can create a new gene by selecting all the points that are in one side
of the plane from Parent A, and all the point that are from the other side of the plane from 
parent B.
Figure \ref{fig:crossover_cpo} show this process in action with a two dimensional representation
of a set of points.
The generation of the random plane is done by selecting three random points from one parent 
($P_A$, $P_B$, and $P_{\perp}$) and then selecting the plane $\pi$ such as the first two points
are included in the plane, and such as, the plane is perpendicular to the plane $\pi*$ that include
all three points.
Algorithm \cref{alg:plane_construction} show a simple procedure to construct such a plane.
The reason tis plane is constructed in this specific manner (rather than simply construct
a plane that include three random points) is that support structures tends to be mostly flat,
therefore with a plane that include three points it is likely that most points would hand up
close to the border, making the division not very equal.
In the algorithm described there is one small edge case, infact it cannot work if there are
less than three points in a plane, or if the three points selected are in a straight line, 
making it impossible to build the plane. In all of this circumstances the algorithm simply
ignores the crossover and return a gene identical to one random parent.


\begin{figure}[h]
    \centering
    \includegraphics[width=0.5\textwidth]{images/crossover_cpo.png}
    \caption{Example of how the crossover is made (in 2 dimensions)}
    \label{fig:crossover_cpo}
\end{figure}


\begin{algorithm}[h]
\caption{Plane Construction}
\begin{algorithmic}[1]
    \Require $p_A, p_B$ Points defining the base line of the plane
    \Require $p_{\perp}$ Point from which distance is maximized
    \Ensure $\pi$ The desired plane

    \Procedure{ConstructPlane}{$p_A, p_B, p_{\perp}$} \Comment{Find the plane that include the three points}
        \State $\pi^* \gets \Call{PlaneFromPoints}{p_A, p_B, p_{\perp}}$
        \State $\mathbf{v} \gets \Call{Normal}{\pi^*}$ \Comment{Normal of plane spanned by $p_A, p_B, p_{\perp}$}
        \State $p_C \gets p_A + \mathbf{v}$ \Comment{Construct third point along the normal direction}
        \State $\pi \gets \Call{PlaneFromPoints}{p_A, p_B, p_C}$ \Comment{Find the plane that include the three points}
        \State \Return $\pi$
    \EndProcedure
\end{algorithmic}
\label{alg:plane_construction}
\end{algorithm}


\subsection{Initialization}
\label{sec:contact_points_opt_init}

The initialization of the genes is done with a simple procedure: First we calculate the area
of the critical surface we need to generate, then we calculate the number of supports that 
need to be generated initially by multiplying the area by a ``support density'' parameter,
finally we randomly generate the desired number of supports by repeatedly randomly
sampling a node, randomly selecting a radius, and adding a support on the selected node
with the selected radius.


\subsection{Optimization Process and Parameters}
\label{sec:contact_points_opt_par}

The optimization process is fairly straightforward, it is composed of at most 2000 generations,
each of them having 100 individuals. Patience is used as an early termination strategy to avoid waisting
cpu cycles, and the maximum number of generations allowed without progress is set to 25.
The selection process is elitist, with the 10 best individual always passing to the next generation,
while the selection of the remaining 90 individuals is done using tournament selections with a 
tournament size of 10.



\section{Contact Points Grouping}
\label{sec:contact_points_grouping}

This stage in the pipeline aim to group contact points based on proximity, in order to optimize
each section individually. As the previous ``grouping'' step, this is not strictly necessary
theoretically, however it essentially required for good performance in practice.
The reason why splitting is acceptable in this scenario is that the support structure
of areas that are far apart, are generally independent from each others. For example,
in our ``Dragon'' testcase we can imagine how the structure generated to support the left
wing is ruffly independent from the structure generated for the right wing.
For this reason optimizing them together gives minimal benefit to the objective function,
however optimizing them separately has big performance benefits. This is because the algorithm
for stiffness evaluation we explained in chapter \ref{cha:stiffness_algo} has a complexity
of $o(n^2 \log (n))$ meaning that with a divide and conquer approach can be highly effective
in reducing the computational complexity of the algorithm.
Initially some simpler ``greedy'' algorithms for the grouping of contact points were tested,
however none of them provided satisfactory results. This tests included strategies such as using the
``critical areas'' as a starting point, and merging them based on proximity, and other similar
heuristics. However we found that with those type of approach it was extremely difficult to regulate
the right amount of ``grouping'' required for different shapes, as they tended to either
group too aggressively, or not grouping enough. For this reason an optimization-based
solution was adopted using a Compositional Pattern Producing Network for generating the groups,
with a genetic algorithm based optimization.
The final result of a grouping step executed on the ``Dragon'' testcase can be seen in figure
\ref{fig:cp_grouping}. To explain the optimization process that led to the result seen in the
picture we will explain each component of the genetic algorithm
individually as we did in the previous section.

\subsection{Gene Structure}
\label{sec:contact_points_grouping_gs}

In the contact point grouping stage the ``gene'' is represented as a Compositional Pattern
Producing Network (CPPN) that take as input the position of a contact points (the $x$, $y$ and $z$ coordinate)
and give as output the group that the node is part of.
To categorize a point into a group we just take the last layer of the network, and pick the group
corresponding to the neuron with the highest output. This means that the maximum number of group
the network can produce is upper bounded by the size of the network. Generally speaking this is not an
issue as the number of groups generated is not particularly high, meaning that even with a small
25 neurons output layer we are not placing significant constraint on the model.
The final topology of the network ended up as a fully connected NN, with the input layer
of size 3, one hidden layer with size of 32, and a Sigmoid activation function, and one 
output layer with a size of 25.
This neural network is tiny by modern standard, and this is done for two reasons: First of all
the task itself is not very complicated, and can be easily performed with such a small network, so
there is no real reason for going bigger. Secondly the training process is not really efficient as
it rely on genetic evolution rather than back-propagation, making shallower network ideal since they
are easier to train.

\subsection{Cost Function}
\label{sec:contact_points_grouping_cf}

The cost function associated with grouping is parametrized by three values
($K_{\text{height}}$, $K_{\text{area}}$ and $K_{\text{volume}}$)
Their use is illustrated in algorithm \ref{alg:cpg_cf}.
The general idea is that once a group is created we compute it's (three dimensional) convex hull
(using the efficient Quick Hull algorithm \cite{quickhull}),
and then apply three main costs:
The first two are proportional to te area and the volume of the convex hull, and are
essentially there to incentivize the algorithm to create groups that contains points
that are close together, in order to minimize the cost. Meanwhile the third one is
a cost that is proportional to the height of the group. This is a regularization therm
that ensure there is a cost in creating a group, otherwise the optimizer would always and up
with a solution that uses the highest amount of group possible.
Generally speaking it is less desirable to create too many groups, because we give less
opportunities to the optimizer to ``merge'' support structure together, and therefore
save on material; This ``undesirability'' is higher for groups with a taller height (defined
as the maximum $z$ of the points in the group), because the taller a point is, the more expensive
it become to generate a support structure that reaches it; This is why the regularization factor
depends on the height, and is not just a constant.

\begin{algorithm}[h]
\caption{Contact Points Grouping Cost Function}
\begin{algorithmic}[1]
    \Require $G$ Set of grouped contact points
    \Ensure $c$ The total cost

    \Procedure{ConstructPlane}{$G$} \Comment{Compute the cost of a set of groups}
        \State $c \gets 0$
        \For {$g \in G$}
            \State $h \gets \Call{ConvexHull}{g}$
            \State $c \gets c + 
                K_{\text{height}} \cdot \Call{Height}{h} +
                K_{\text{area}} \cdot \Call{Area}{h} +
                K_{\text{volume}} \cdot \Call{Volume}{h}$
        \EndFor
        \State \Return $c$
    \EndProcedure
\end{algorithmic}
\label{alg:cpg_cf}
\end{algorithm}

\subsection{Mutations}
\label{sec:contact_points_grouping_mut}

Defining mutations on a neural network (especially if the network is small and shallow like ours)
is particularly easy, as the network can be seen as a set of weights we need to tune. For this reason
the mutation is parametrized by 4 parameters. A mutation rate ($p_m$) a reset rate ($p_r$)
and two random distribution for mutation and reset ($\mathcal{D}_m$ and $\mathcal{D}_r$).
With this four parameters the mutation can be easily described with algorithm \ref{alg:network_mut}.
In the final implementation we ended up defining four different set of the four parameters,
and randomly picking one for every mutation operation.
This was done in order to increase the stochasticity of the mutation, that is generally
speaking a good idea for genetic algorithms.

\begin{algorithm}[h]
\caption{Mutation of neural network}
\begin{algorithmic}[1]
    \Require $N$: The network to mutate
    \Require $p_m \in [0, 1]$: Neuron mutation probability
    \Require $p_r \in [0, 1 - p_m]$: Neuron reset probability
    \Require $\mathcal{D}_m$: Arbitrary probability distribution for mutation 
    \Require $\mathcal{D}_r$: Arbitrary probability distribution for reset
    \Ensure $N^*$: The mutated network

    \Procedure{MutateNetwork}{$G$} \Comment{Compute the cost of a set of groups}
        \State $N^* \gets \emptyset$ \Comment{Initialize empty network}
        \For {$n \in G$} \Comment{Iterate over the parameters of $G$}
            \State Sample $x \sim \mathcal{U}(0,1)$
            \If{$x < p_m$} \Comment{Weight mutation}
                \State Sample $m \sim \mathcal{D}_m$
                \State $n^* \gets n + m$
            \ElsIf{$x < p_m + p_r$} \Comment{Weight reset}
                \State Sample $r \sim \mathcal{D}_r$
                \State $n^* \gets r$
            \Else
                \State $n^* \gets n$
            \EndIf
            \State $N^* \gets \Call{AddParameter}{G^*, n^*}$ \Comment {Adding the mutated weight to the new network}
        \EndFor
        \State \Return $N^*$ \Comment {Returning the fully mutated network}
    \EndProcedure
\end{algorithmic}
\label{alg:network_mut}
\end{algorithm}

\subsection{Crossover}
\label{sec:contact_points_grouping_cross}

Crossover is once again simple in the case of neural network (Especially
considering that the size and shape of the network is known ``a priori'' and is
not part of the crossover/mutation), in this case we have defined three different crossover
strategies, and every time a crossover is executed we randomly pick one of them.
The three strategies selected are:
\begin{itemize}
    \item \textbf{Uniform:} This is the traditional uniform mutation where every node in the offspring's network
    is either inherited from Parent A or form parent B with 50-50 probability.
    \item \textbf{Single Point:} In this case a random number is generated between zero and the number of parameters,
    and then all of the weights that have an index lower than the generated number are inherited from one
    parent, while the remaining one are inherited from the other.
    \item \textbf{Arithmetic:} In this case we decide a parameter $\alpha$ (usually 0.5) and then the weights of the
    offspring ($\mathbf{\theta}_{o}$) can be expressed as a weighted summation of the weights of the two parents
    ($\mathbf{\theta}_{A}$ and $\mathbf{\theta}_{A}$) using the simple equation: $\mathbf{\theta}_{o} = \alpha \mathbf{\theta}_{A} + (1 - \alpha)\mathbf{\theta}_{B}$
\end{itemize}

\subsection{Initialization}
\label{sec:contact_points_grouping_init}

Initialization of the network is achieved using the famous ``He'' initialization technique
first describe in the famous 2015 paper ``Delving Deep into Rectifiers: Surpassing Human-Level Performance on ImageNet Classification''
\cite{he2015}.
``Xavier'' initialization \cite{xavier2010} were also tested, but were found to have slightly worst
performances compared to He.




\subsection{Optimization Process and Parameters}
\label{sec:contact_points_grouping_par}

The optimization process is composed of at most 2000 generations,
each of them having 100 individuals. Patience is used as an early termination strategy to avoid waisting
cpu cycles, and the maximum number of generations allowed without progress is set to 100.
The selection process is elitist, with the 10 best individual always passing to the next generation,
while the selection of the remaining 90 individuals is done using tournament selections with a 
tournament size of 10.
During our testing we found that this optimization problem war really sensitive to the initialization
of the neural network. Therefore, to reduce variability the optimization process is repeated 5 times,
and only the best output is selected. The decision of doing so was also made easier by the fact 
that this step is by far the faster, takin no more than a few seconds.
